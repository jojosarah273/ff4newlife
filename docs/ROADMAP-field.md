# Roadmap — the field scene

End goal: reproduce all events and gameplay of FF4. We are still building the
**primitives** the events hang on, and still only in the **field scene**.

Legend: ✅ done · ▶ next · ☐ pending

## F1 — Warps and map transitions ▶

The data is already exported (`data/world/maps/<id>.json` carries `triggers`
with `kind: "teleport"`, `map`, `tx`, `ty`).

1. **Teleport triggers** — on entering a cell whose trigger is a TELEPORT,
   warp: `map_id = t.map`, `x = t.tx`, `y = t.ty`, `facing = t.direction`,
   then reload. (Original: `Trigger` in `field/trigger.asm`; the map stack
   push/pop is in `FF4_EVT_MAP` handling.)
2. **Exit tiles** — tile `byte2 & 0x10` pops the previous-map stack
   (`$172C` ring, already modelled in `FF4_WorldState.prev_map`).
3. **Door tiles** — tile `byte1 & 0x10`; open the door, step in, warp.
4. **Wipe-in** — the original plays `WipeIn` after `LoadMap`; our equivalent
   is a short fade/iris on the tilemap, not a hardware effect.
5. **Collision on arrival** — verify the destination cell is walkable; the
   original does not check, so a bad target would trap the player.

Acceptance: walking off Baron's south edge lands on the world map at the
matching coordinates, and walking back returns to Baron.

Acceptance: `NEW GAME` produces a party identical to the ROM's (stats, gear,

## F3 — Events and triggers ☐

We already have the VM (`ff4_event_step`, 256 scripts validated). What is
missing is the *field wiring*:

1. **Trigger tiles** → `triggerScript[map]` → event VM (blocking; the field
   freezes while `$b1` is set).
2. **NPC talk** → `npcScript[npc]` / `npcEventCalls`.
3. **Dialogue** → the VM's `DIALOG`/`DIALOG2`/`DIALOG3` actions feed
   `draw_dialog` (replace the test pages).
4. **Scene requests** → battle, shop, inn, warp, song, fade: the VM already
   emits `FF4_EventAction`; the scene machine dispatches them.
5. **Movement actions** → NPC/actor walk commands (`ACT obj/act`).

Acceptance: the opening's Baron scene runs from the real event script and
every dialogue line comes from `eventDialog1/2`.

## Discipline (unchanged)

* every constant is verified against the ROM and pinned by
  `tests/test_world_rules.c` (396 checks);
* every asset is regenerated by `node tools/export_resources.js`
  (asm-sourced palettes + window tiles, rip blobs mirrored);
* no SNES hardware concepts leak into the engine — the field scene is a
  2D tilemap, a camera and a sprite list.

## Known gaps / risks

* **Window art**: the dialogue window is drawn with primitives; the real
  9-slice needs the correct BG3 tile bank (tile `0x16` ≠ `WindowGfx` tile
  `0x16`; the `$2840/$2860/$2C00` writes are tilemap rows).
* **Original glyphs**: the font tiles are not yet located (`adc #$82` is the
  char→tile base but that bank decodes to stripes), so text uses `ff4.ttf`.
* **Field tile art**: `mapTilesets`/`mapGraphics` in the rip are not in the
  ROM's byte layout; sub-map rendering still needs that mapping.

## Appendix: palette + layers (verified references, for the next pass)

### Palette — `LoadMapPal` (`field.asm @c1f9`)

```asm
lda $0fe0            ; map palette id
sta $19 / stz $18    ; 16-bit value = pal<<8
lsr $19 / ror $18    ; -> x = pal*0x80   (the palette's BYTE offset)
ldy #$0020
loop: lda f:MapPal+$10,x : sta $0cdb,y    ; LOW byte
      lda f:MapPal+$90,x : sta $0ceb,y    ; HIGH byte  (0xCEB = 0xCDB+0x10)
      inx : iny
      tya and #$0f : bne loop
      tya clc adc #$10 : tay
      bne loop
```

So MapPal is a **split lo/hi table**, *not* 16-bit LE pairs:
`colour[n] = MapPal[x + 0x10 + n] | (MapPal[x + 0x90 + n] << 8)`, `x = pal*0x80`,
128 colours, placed in 8 blocks of 16 at CGRAM byte offsets `0x20,0x40,…,0xE0`.

Verified: palette table base is **`0xA5E00`** (headerless), and palette 4
contains **4 of the 7** colours measured from the real Kaipo map
(sand `(224,208,152)`, water `(92,158,250)`, olive `(102,102,78)`,
dark blue `(38,83,135)`).

**Remaining discrepancy:** the tile→palette-index mapping. We use
`index = group*8 + pixel` with `group = (hi>>2)&7`. Since the palette holds 4
of the real colours, the table and base are right; the *group/colour* split is
what still differs. Next test: render Kaipo with `index = pixel*8 + group`
and score against the 7 measured colours (the two orderings differ by one
colour in the current render, so this is a small, contained change).

### Layers — two tilesets per cell

`LoadSubMap` (`field.asm @83a4`) copies `MapTileset` into **four** VRAM banks:

| VRAM | bank | layer |
| --- | --- | --- |
| `$4800` | +0x00 | BG1 low |
| `$4880` | +0x80 | BG1 high |
| `$4900` | +0x100 | **BG2 low** |
| `$4980` | +0x180 | **BG2 high** |

`ReloadSubMap`: `$212C = $17` (BG1|BG2|BG3|OBJ), `$2105 = $09` (mode 1, BG3
high priority). `InitBG1Tilemap` / `InitBG2Tilemap` build both layers from the
same 32-wide layout.

* tilemap entry **bit 13 (priority)** = draw above OBJ → "walk under the
  bridge"
* tile props `byte2 & 0x04` = hide sprite on lower z, `& 0x08` = hide bottom
  of sprite → the two partial-occlusion cases
* `byte1 & 0x03` z lanes, `& 0x04` bridge, `& 0x0A` floor

Engine translation:

```
per cell: bg1{tile,pal,pri,hf,vf}, bg2{tile,pal,pri,hf,vf},
          floor, z, bridge, hide_sprite, hide_bottom
draw:  BG1 -> actors -> BG2 (pri cells only) -> windows
clip:  hide_sprite => skip actor;  hide_bottom => clip its lower 8px
```
